### Fixed

- Stored credentials (LDAP binds, integration tokens, AI provider keys, TSIG secrets, backup-target passwords) were encrypted under a key derived from `SECRET_KEY` on most installs, because nothing generated `CREDENTIAL_ENCRYPTION_KEY`, and the appliance generated one and never passed it to the api. New writes now use `CREDENTIAL_ENCRYPTION_KEY` when it is set, with the `SECRET_KEY`-derived key kept as a read fallback so nothing already stored stops working, and `python -m app.core.rotate_credential_key` moves existing values onto the dedicated key (idempotent, resumable, audited). The Helm chart and the appliance now generate and keep the key, and the api logs a warning while none is set. On Compose and hand-written Kubernetes manifests, set `CREDENTIAL_ENCRYPTION_KEY` and run the command; see "Moving stored credentials onto a dedicated key" in `docs/deployment/DOCKER.md`. (#1358)
